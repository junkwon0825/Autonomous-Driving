# Automotive Software Engineering 학습 및 프로젝트 적용

## 목적

자동차 소프트웨어 개발 프로세스의 기초 개념을 학습하고, 이 저장소의 LKAS 제어와 Lane Segmentation 프로젝트에 요구사항 관리, 추적성, 검증·확인(V&V) 관점을 적용한다.

이 문서는 학습 정리와 개인 프로젝트 적용 사례다. ISO 26262 인증, Automotive SPICE 평가, 양산 개발 프로세스 수행 또는 기능안전 적합성을 주장하지 않는다.

## 핵심 개념

### 요구사항 관리

요구사항은 시스템이 제공해야 하는 기능이나 만족해야 할 품질·제약을 명확하고 시험 가능한 문장으로 정의한다. 좋은 요구사항은 하나의 의도를 담고, 모호한 표현을 피하며, 가능하면 관찰 가능한 조건과 합격 기준을 포함한다.

- **기능 요구사항:** 시스템이 수행할 동작
- **인터페이스 요구사항:** 컴포넌트 사이 신호, 단위, 방향, 주기와 오류 처리
- **성능 요구사항:** 측정 방법과 조건이 있는 정량 기준
- **안전 관련 요구사항:** hazard/risk 분석에서 도출되고 안전 계획과 할당 근거를 갖는 요구

요구사항은 설계, 구현, 시험과 변경 영향 분석에 연결한다. 요구사항 ID, 버전, 출처, 책임자, 검증 방법과 상태를 기록하면 변경의 범위와 누락된 시험을 확인하기 쉽다.

### V-Model

V-Model은 개발 단계의 산출물과 그 산출물을 확인하는 시험 단계를 대응시켜 생각하는 개발·검증 관점이다. 실제 조직의 프로세스는 반복·증분 개발과 변경관리를 함께 사용할 수 있다.

| 개발/정의 단계 | 대응하는 확인 단계 | 예시 |
|---|---|---|
| 사용자/차량 수준 요구사항 | 차량 수준 validation | 실제 사용 맥락과 차량 수준 요구를 만족하는가 |
| 시스템 요구사항 및 아키텍처 | 시스템 통합 시험 | 시스템 인터페이스와 시스템 요구사항이 맞는가 |
| 소프트웨어 요구사항 및 아키텍처 | 소프트웨어 통합 시험 | 컴포넌트 인터페이스와 소프트웨어 요구사항이 맞는가 |
| 상세 설계 | 단위 시험 | 함수/모듈의 입력, 출력, 경계조건이 설계와 맞는가 |
| 구현 | 정적 분석·코드 리뷰·단위 시험 | 코드가 설계 규칙과 구현 의도에 맞는가 |

시험은 하위 단위에서 상위 시스템으로 쌓아 올리며, 각 단계는 정의된 요구사항과 합격 기준을 바탕으로 수행한다. 시험을 많이 했다는 사실만으로 요구사항 충족, 안전성 또는 제품 적합성이 자동으로 입증되는 것은 아니다.

### Verification과 Validation

- **Verification:** 산출물이 명세·설계·요구사항에 맞게 만들어졌는지 확인한다. “제품을 올바르게 만들었는가?”
- **Validation:** 의도된 사용 환경과 사용자 요구에서 제품이 필요한 목적을 달성하는지 확인한다. “올바른 제품을 만들었는가?”

코드 단위 시험은 verification 근거가 될 수 있다. 대표적인 실제 사용 조건에서의 사용자/차량 수준 평가는 validation 근거가 될 수 있다. 동일 시험 결과가 두 질문 모두에 답한다고 가정하지 않는다.

### ISO 26262 기초

ISO 26262는 도로 차량의 전기·전자 시스템에서 기능안전 활동을 체계화하는 표준이다. 기능 오작동이 위험 상황으로 이어질 수 있는 경우, item 정의와 hazard analysis/risk assessment, 안전 목표 및 ASIL 결정, 시스템·하드웨어·소프트웨어 안전 요구사항과 아키텍처, 구현·검증, 안전 확인 및 생산·운영 관련 활동을 수명주기 관점에서 다룬다. 지원 프로세스에는 안전 계획, 구성·변경 관리, 검증, 문서화와 확인 조치 등이 포함된다.

ASIL은 프로젝트에서 임의로 붙이는 품질 등급이 아니다. 차량 수준 hazard analysis와 노출·제어 가능성·심각도에 대한 평가, 표준의 절차 및 근거가 필요하다. 이 저장소의 교육용 LKAS 시뮬레이션은 HARA, safety goal, ASIL 할당, safety case, 독립 안전 평가 또는 ISO 26262 준수 산출물을 수행하지 않았다. 따라서 이 프로젝트를 “ISO 26262 준수” 또는 “기능안전 검증 완료”라고 표현하지 않는다.

Automotive SPICE는 자동차 개발 프로세스의 역량을 평가하는 별도 프로세스 참조/평가 모델이다. ISO 26262 기능안전 표준과 목적이 같지 않으며, 이 저장소는 공식 프로세스 평가를 수행하지 않았다.

## 저장소 프로젝트에 적용한 추적성 예시

### LKAS 제어

| 요구사항/주장 | 설계·구현 위치 | 확인 근거 | 해석 범위 |
|---|---|---|---|
| MATLAB에서 기준 모델 시나리오를 실행한다 | `matlab/lkas_reference_simulation.m`, `matlab/lkas_scenarios.m` | `tests/test_lkas_reference.m`, 7개 시나리오 실행 | 결정론적 모델 시험 |
| 조향 명령은 설정 한계를 넘지 않는다 | 조향 saturation 로직 | 각 시나리오의 saturation assertion 및 결과 CSV | 설정된 모델 한계에 대한 검증 |
| 저장 성능 지표는 시나리오 출력과 일치한다 | `matlab/run_lkas_suite.m` | metrics CSV와 재계산 지표 비교 | 저장 데이터의 일관성 확인 |
| 미니카 프로젝트와 MATLAB 결과를 분리한다 | LKAS README와 문서 구조 | MATLAB 결과 CSV/PNG와 미니카 별도 기술 문서 | 두 시스템 사이 실측 성능 비교를 의미하지 않음 |

상세 ID, 상태와 실행 기록은 [요구사항·추적성 문서](../lkas-control-mini-car/docs/requirements-and-traceability.md)에 있다. 이 추적표는 교육용 프로젝트의 산출물 관리 예시이며, 기능안전 요구사항이나 안전 인증 자료가 아니다.

### Lane Segmentation

기존 프로젝트의 데이터, 학습, 평가 산출물을 요구사항-검증 관점으로 연결한 예시다. 이는 별도의 안전 요구사항 세트나 공식 기능안전 추적표를 의미하지 않는다.

| 개발 산출물 | 프로젝트에서 관리하는 내용 | 검증/평가 예시 |
|---|---|---|
| 데이터 요구/정의 | 이미지-mask 쌍, 라벨 분포, 날짜 그룹 분할 | 파일·크기·열기 검사와 데이터셋 보고서 |
| 모델/학습 설계 | U-Net, loss, optimizer, seed, checkpoint 선택 | 고정 validation 그룹에서 학습/평가 |
| 성능 기준/평가 | BCE, Dice, IoU, precision/recall, threshold | validation 지표와 Kaggle 평가 점수를 별도로 보고 |
| 결과 및 한계 | best/failure 사례와 실험 설정 | 실제 결과물·로그를 README와 experiment log에 연결 |

모델 성능 지표는 주어진 데이터 split과 평가 절차에 대한 결과다. 이는 도로 환경에서의 인지 안전성, 위험 분석, 차량 기능 validation이나 ISO 26262 산출물을 대신하지 않는다.

## 변경 및 시험 관리 체크리스트

프로젝트 요구사항이나 구현을 변경할 때 다음을 확인한다.

1. 요구사항 ID와 합격 기준을 명확히 한다.
2. 영향받는 인터페이스, 설계, 코드, 데이터 및 downstream 기능을 찾는다.
3. 정상 조건뿐 아니라 경계값·오류 조건과 입력 유효성을 정의한다.
4. 요구사항별 검증 방법, 시험 데이터/환경, 결과와 실행 버전을 기록한다.
5. 실패와 미시험 항목을 성공으로 간주하지 않고 추적표에 남긴다.
6. 요구사항 변경 시 관련 설계·구현·시험 결과를 함께 갱신한다.
7. 기능안전 주장을 해야 하는 제품 개발에서는 별도의 safety lifecycle, 안전 계획, 독립 확인 및 조직 프로세스를 적용한다.

## 이력서용 요약 예시

> 자동차 소프트웨어 공학 교육을 통해 ISO 26262, V-Model 기반 개발 프로세스, 요구사항 관리 및 소프트웨어 검증·확인(V&V)의 기초를 학습하고, MATLAB 기반 LKAS 제어 프로젝트에 요구사항과 시험 항목의 추적성 개념을 적용했습니다.

면접에서는 다음처럼 프로젝트별 역할을 구분해 설명한다.

- **LKAS:** 차량 동역학 모델과 제어기 구현 및 시뮬레이션 기반 제어 성능 분석
- **Lane Segmentation:** 데이터 분할, 딥러닝 모델 학습·평가 및 인지 결과 분석
- **Automotive Software Engineering:** 요구사항-설계-구현-시험 간 연결, V-Model과 V&V의 기초 이해 및 적용 사례

교육 이력과 본인의 실제 참여 범위에 맞게 문장을 조정한다. 수료하지 않은 교육이나 수행하지 않은 안전 프로세스는 이력서에 사실처럼 기재하지 않는다.

## 참고 범위와 한계

이 자료는 ISO 26262 및 Automotive Software Engineering의 학습 노트이며 표준 전문이나 조직의 개발 절차를 대체하지 않는다. 실제 제품의 표준 적용은 적용 판본, item 범위, safety plan, 조직 역할, tailoring과 객관적 work product에 따라 판단해야 한다.
